# PostgreSQL Migration Spec

Date: 2026-02-28
Project: paywall-api

## Objective
Migrate the service from SQLite to PostgreSQL before deployment.

## Decisions Locked
- Migration approach: direct cutover to PostgreSQL
- Driver: pgx (database/sql compatible)
- Write model: normal concurrent DB writes with pooling (no serialized writer queue)
- Data migration: no historical SQLite data migration; start PostgreSQL fresh

## Scope
Update DB connection/runtime, migration runner, SQL migrations, query syntax, and operational docs/tools so the service runs on PostgreSQL in deployment.

## Implementation Requirements

### 1) Database bootstrap and config
- Replace SQLite-specific connection setup with PostgreSQL DSN-based setup.
- Use `DATABASE_URL` (or equivalent PG env vars) as the primary runtime connection input.
- Remove SQLite-specific PRAGMA and lock tuning.
- Configure reasonable PostgreSQL pool settings (max open, max idle, conn lifetime).

### 2) Migration runner compatibility
- Replace SQLite migrator driver usage with PostgreSQL-compatible migrator wiring.
- Ensure migration source path handling remains stable for local and deployment runs.

### 3) SQL migration files
- Rewrite schema SQL from SQLite dialect to PostgreSQL dialect.
- Convert SQLite patterns:
  - `INTEGER PRIMARY KEY AUTOINCREMENT` -> `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (or equivalent)
  - `DATETIME` -> `TIMESTAMPTZ`
  - table rebuild patterns for dropping columns -> direct PostgreSQL `ALTER TABLE ... DROP COLUMN`
- Preserve functional schema intent and indexes/constraints.

### 4) Query and write-path SQL changes
- Convert placeholders from `?` to `$1, $2, ...`.
- Convert idempotent insert behavior:
  - `INSERT OR IGNORE` -> `INSERT ... ON CONFLICT DO NOTHING`
- Remove reliance on `LastInsertId()` and use `RETURNING` where inserted IDs are needed.
- Remove SQLite-only lock retry behavior and serialized writer queue path; use concurrent pooled writes.

### 5) Tooling updates
- Update or retire SQLite-only tools that reference:
  - `sqlite_master`
  - `sqlite_sequence`
  - SQLite maintenance commands like `VACUUM`
- Keep utility behavior aligned with PostgreSQL system catalogs and SQL syntax.

### 6) Documentation and startup workflow
- Update docs and startup scripts to describe PostgreSQL-first setup and run flow.
- Ensure env var examples and migration instructions are deployment-accurate.

## Out of Scope
- Supporting both SQLite and PostgreSQL simultaneously in production code.
- Migrating old SQLite data into PostgreSQL.
- New product features unrelated to DB migration.

## Acceptance Criteria
- `go build ./...` succeeds.
- Migrations apply cleanly to a fresh PostgreSQL database.
- Core endpoints function with PostgreSQL:
  - `/health`
  - `/leaderboard`
  - `/pay`
  - `/webhook`
  - `/total`
- Webhook idempotency remains correct under PostgreSQL (`ON CONFLICT DO NOTHING` path).
- No runtime SQLite-only SQL/driver references remain in active code paths.

## Verification Checklist
1. Install/update Go dependencies and run `go mod tidy`.
2. Run `go build ./...`.
3. Run migrations against an empty PostgreSQL DB.
4. Start API and smoke test all core endpoints.
5. Replay webhook events and confirm correct insert/update behavior.
6. Run a small concurrent request test to validate pooled write behavior.

## Risks
- SQL dialect conversion gaps in edge query paths.
- Migration ordering or schema drift if old SQLite assumptions remain.
- Operational misconfiguration (SSL mode, DSN format, pool sizing) at deploy time.

## Rollback Strategy
- Roll back application deployment to previous image/revision.
- Roll back database schema using down migrations when safe.
- Keep pre-cutover SQLite artifact for emergency reference only (not active runtime).
